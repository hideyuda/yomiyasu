# 用途プロファイルの動作確認（エージェントによる通し検証）

用途プロファイルを追加したSKILL.mdを、別のエージェントに通常の利用と同じ形で使わせ、出力と指示の分かりにくさを確かめた記録です。エージェントには変更の意図を伝えず、SKILL.mdと参照ファイルだけを読ませました。

## 条件

- 実行したモデル: Claude Sonnet 5.5（A、B）、Claude Opus 5.5（C、D）
- 入力: `tests/corpus/raw_ai/` の文章と、`evals/comparison_benchmark.md` セットBのAI生成文（以下「セットB」）
- 依頼文は、行き先だけを伝える自然な言い方にしました。
- スコアは、出力後に修正したリンターで測り直した値です（同じプロファイルで入力と出力を測っています）。

| ID | 入力 | 依頼 | プロファイル・方法 | スコア（入力 → 出力） |
|---|---|---|---|---|
| A1 | 04_slack_announce（default） | Slackの#generalに投稿するので整えて | chat・整える | 100 → 100 |
| A2 | セットB | 社内ブログに載せたいので読みやすく | article・整える | 56 → 95 |
| B1 | 08_essay_retrospective（formal） | Xに投稿する形に | sns・書き分ける | 89 → 98 |
| B2 | 03_pr_description（default） | チームのSlackで共有したい | chat・書き分ける | 90 → 100 |
| C1 | 01_tech_arch（formal） | 提案資料のスライド1枚分に | proposal・書き分ける | 100 → 98 |
| C2 | 08_essay_retrospective（formal） | noteに載せたい、硬すぎるので柔らかく | article・整える | 96 → 98 |
| D1 | セットB | Slackでチームに共有したい | chat・書き分ける | 50 → 100 |
| D2 | セットB | Xで紹介したい | sns・書き分ける | 21 → 100 |
| D3 | セットB | 読みやすくして（行き先なし） | プロファイルなし | 60 → 100 |

すべての依頼で、エージェントは想定どおりのプロファイルと方法を選びました。行き先を伝えないD3はプロファイルを使わず、従来のyomiyasuと同じ規則で書き直しています。

リンターのスコアは問題がないことを示すだけで、行き先に合っているかは示しません。C1の入力は地の文の設計メモですが、proposalで測っても100点です。出力の良し悪しは、下のとおり人が読んで判断しました。

## 出力の例

D2（セットBをXの投稿に書き分けたもの）は、元の主張と3つの原則を残したまま、全角138字に収まりました。

```text
非同期処理でいちばん気をつけたいのは、ネットワークの瞬断。
メッセージを流すだけだと、知らないうちにデータがおかしくなる。

地味だけど役に立つのはこの3つ。
・冪等性を保ち、重複した処理はスキップ
・リトライは指数バックオフでDBの負荷を抑える
・処理に失敗したメッセージはDLQに隔離
```

B2（PR説明文をSlack向けに書き分けたもの）では、元の10項目をすべて残し、変更の4点を箇条書きにしています。

```text
今回の変更は4点です。
・期限切れが近いトークンをキューに登録し、ワーカーがリフレッシュを処理します
・同一ユーザーのジョブは、ユーザーID単位で重複排除します
・失敗時の再試行は、指数バックオフで最大3回までです
・上限に達したら、再ログインを促す状態へ遷移させます
```

プロファイルなしのyomiyasuは、A1と同じSlackのお知らせを書き直すとき、お願いの3項目を地の文にまとめ、「インフラチームは」を2回足していました（`tests/corpus/yomiyasu_rewritten/04_slack_announce_sonnet_default.md`）。A1では箇条書きが残り、主語も足されていません。

## 見つかった問題と直したこと

| 問題 | 出たところ | 直したこと |
|---|---|---|
| 「・」の箇条書きを地の文として数え、同じ文末の連続を誤って警告した | B2、D1 | プロファイルを使うときは「・」の行を箇条書きとして扱う（プロファイルなしの結果は変えない） |
| Xの文字数がレポートに出ず、エージェントが自分で数えていた | B1 | レポートに投稿ごとの文字数を出す |
| スライドのタイトルが長い（43字） | C1 | タイトルを40字以内の目安にし、リンターでも知らせる |
| Xへの書き分けで、具体的な事実（ADR、PRの完了条件）を削り、抽象的な教訓を1行目に置いた | B1 | 削る順番を決め、数字ややったことを最後まで残す。1行目に元の文にない教訓を置かない |
| 意味が読み取れない文を、言い換えて別の行き先へ書き写した | D1 | 書き分けるときは、意味が読み取れない文をメモから外して書き手に確かめる |
| 空欄 `[ここに一言]` が、指示語で始まる文の直前に入った | C2 | 整えるときは本文に空欄を入れず提案だけにする。書き分けるときも段落の終わりに置く |
| 整えるときに、硬さ辞書や並列情報の箇条書き化をしてよいかが分からない | A1、A2、C2 | 「直す必要のあるところ」に、硬さ辞書とプロファイル特有のAIっぽさを含めると明記 |
| チャットで「お疲れ様です」を足すかどうかが分からない | A1、B2、D1 | 元の文にあるか、書き手の実例で使っているときだけ付ける |
| 書き分けたときの「変えたところ」の書き方が決まっていない | B1、B2、C1、D2 | 外した一般論、削った項目、足した定型、順番の入れ替えを1行ずつ書く形にした |
| 漢数字を算用数字にしてよいかが分からない | B1、C2 | 用途プロファイルでは数量を算用数字にする |
| 「柔らかく」という依頼で常体を敬体に変えてよいかが分からない | C2 | 依頼だけでは文体を変えず、書き手に尋ねる |
| SKILL.mdからslop-catalog.mdへの案内がない | C、D | Step 2に案内を足した |

## 本家の規則に関わるため、今回は直していないもの

- 「黙ってスキップ」のように、意図した設計としての「黙って」を「気づかないうちに」と直すと、不具合のように読める（A2、D1、D3）。
- slop-catalog.mdは「落とし穴」を言い換え対象にしているが、SKILL.mdの慣用句の基準では残す側にも読める（A2、D3）。
- 300字前後の短い文章では、箇条書き3行や太字1か所でも比率の警告が出る（A2）。
